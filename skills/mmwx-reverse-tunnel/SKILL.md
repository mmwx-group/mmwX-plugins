# 反向隧道(妙妙屋X)

目标:目标机(在 NAT 后面)主动拨 WireGuard 到入口机,入口机用隧道的内网地址连目标,不需要目标有公网入站。

## 前提

- 入口机有公网地址,并且能放行一个 **UDP 端口**(默认从 51820 起,以创建结果里的 `tunnel_endpoint` 为准)。
- 两台的 agent 都在线(`server_list` 看状态),版本不低于 v1.0.0。
- 跑在容器里的 agent 需要 `/dev/net/tun` 和 `NET_ADMIN`。

## 步骤

1. `server_list` 找到入口机(有公网)和目标机(NAT 后面)的 ID。
2. `reverse_tunnel_list` 看这一对是否已经有隧道,有就直接用。
3. `reverse_tunnel_create`:`entry_server_id` + `target_server_id`。
4. 再 `reverse_tunnel_list` 确认状态是已连接,并记下这条隧道的 **`target_addr`**(入口机连目标用的内网地址)。
   - **每条隧道的地址都不一样**。两台入口连同一台目标,是两条隧道、两个不同的 `target_addr`,不能互抄。
5. 让入口机上的流量走隧道,二选一:
   - **端口转发**:在入口机上建转发入站,目标地址写 `target_addr`,端口写目标机上入站**实际监听**的端口。
   - **路由出站**:入口机上指向目标的出站,把服务器地址从目标的公网地址改成 `target_addr`(目前要手动改出站配置,建路由出站时不会自动换)。

## 核对是不是真的走了隧道

节点列表里显示的「原服务器地址」是节点自己记的落地公网地址,**不代表实际走向**。要看入口机的 xray 配置:

- `server_inbound_list`(入口机)里转发入站的目标地址是 `198.19.x.x` → 走隧道。
- `server_inbound_outbounds`(入口机)里出站的服务器地址是 `198.19.x.x` → 走隧道;是公网地址 → 直连。

## 排障

- **状态一直不是已连接**:入口机的防火墙 / 云安全组没放行 `tunnel_endpoint` 的 UDP 端口,这是最常见的原因。
- **提示 agent 离线或版本过低**:两台都要在线且 ≥ v1.0.0;`server_agent_upgrade` 升级。
- **隧道已连接但转发不通**:端口写成了公网映射端口。经隧道要用目标机本机监听的端口。
- **目标机上的入站只监听了 127.0.0.1**:改成监听所有地址,否则从隧道地址连不进去。

## 注意

- `reverse_tunnel_delete` 需要 `confirm: true`。删掉后,还在用它内网地址的端口转发和出站会立刻不通,删之前先 `reverse_tunnel_list` 看「有几条端口转发在用」。
- 隧道只负责打通内网,不改变计费和用户凭据。
